Request Bucket System Architecture

Each visitor gets a bucket with a public URL and a private owner_token. Anything sent to that URL is captured, stored twice — once as a full raw document, once as a queryable summary — and pushed live to anyone watching over an open WebSocket.


How a request becomes a live update

1

Create. The browser POSTs /buckets. bins.py inserts a Bucket row in Postgres and returns its public_id and owner_token; the browser saves the token to localStorage and routes to /bin/:publicId.

2

Inspect. On that page the browser calls GET /buckets/{id} (with the Owner-Token header) for history, and opens WS /ws/{bucket_id}; websocket.py checks the bucket exists, then hands the socket to connection_manager.

3

Capture and broadcast. Any method sent to /{public_id}/{path} lands in catch_all.py, which writes the full raw request to MongoDB, a summarized row to Postgres, then calls connection_manager.broadcast() — pushing the new request to every open socket for that bucket, live.

Working with AI

Keeping the architecture ours

Every PR was reviewed as a team. Architecture was determined prior to coding. Claude Code was used first in "plan mode" and in "manual approval" mode.

Where it cost us

Some Linear issues had overlapping scope, which led to some PR reviews being more involved.

Takeaways

Iterate and test in discrete chunks.

Function over form.

Establish baseline architecture before designing features.

Opt for simple and robust over clever and verbose.
